WHY THIS FILE EXISTS
--------------------
All ML numbers so far come from the WinLOLBIN-GT dataset. That dataset is
synthetic and close to saturated, so the report needs an honest external check
on real Windows telemetry. Your job is to collect authorised Sysmon Event ID 1
records on an isolated VM and hand them back in a fixed format. I will adapt
them to the model schema and produce the validation numbers. You do not need to
run or report ML metrics yourself.


1. SCOPE, SAFETY AND AUTHORISATION (DO THIS FIRST)
--------------------------------------------------
- Use an isolated Windows VM only. No production systems, no shared lab hosts.
- Take a clean snapshot before installing Sysmon or running tests, and roll
  back after collection.
- Disable or disconnect network access for the attack-simulation runs. If a
  test needs a local file, create it locally.
- Use harmless payloads only (e.g. calc.exe, notepad.exe, a local .inf). No
  real malware, no credential dumping, no lateral movement, no persistence that
  survives the snapshot.
- Confirm scope and permission with the instructor before running anything.
- Keep a written authorisation/safety note in docs/ (one paragraph is enough:
  who authorised it, VM name, date, network state, rollback plan).
- If any step feels unsafe or out of scope, stop and ask. A missing experiment
  is better than an unsafe one.


2. WHAT TO INSTALL AND ENABLE
-----------------------------
- Windows 10/11 VM, fully patched enough to run Sysmon.
- Sysmon (Microsoft Sysinternals) with a maintained config, e.g. SwiftOnSecurity
  or sysmon-modular. Minimum: process creation (Event ID 1) and network
  connection (Event ID 3).
- Confirm Event ID 1 is being written:
    Get-WinEvent -LogName "Microsoft-Windows-Sysmon/Operational" -MaxEvents 5
- Set the VM clock to UTC and keep it there. Record timestamps in UTC.
- Note the Sysmon version, config file name/hash, Windows build, and VM name in
  your notes. These belong in the report's limitations section.


3. REQUIRED OUTPUT FILES
------------------------
data/raw/vm/sysmon_events.csv

Do not commit large raw logs if the repo rules say not to; keep them in
data/raw/vm/ locally and tell me where they are.


4. COLLECTION PLAN (SUGGESTED)
------------------------------
Benign workload (label 0), run as a normal user and as admin:
  whoami, whoami /claims, ipconfig /all, tasklist, net user, systeminfo
  certutil -store My
  robocopy C:\Users\Public\test C:\Users\Public\test_copy /E
  powershell -NoProfile -Command "Get-Command -Syntax whoami"
  msiexec /i <a small locally built MSI> /qn
  regsvr32 /s <a harmless local DLL>   (only if you have a safe DLL)
  schtasks /query
  bitsadmin /list /allusers
Record each as its own benign scenario so the model sees realistic noise.

Attack simulations (label 1), authorised Atomic Red Team or equivalent manual
commands with harmless payloads:
  T1059.001  PowerShell encoded/hidden command (payload: calc.exe or Write-Output)
  T1047      WMI process creation (wmic process call create calc.exe)
  T1569.002  PsExec-style service execution against the local VM only
  T1218.003  CMSTP with a local .inf
  T1218.005  Mshta with a local .hta that opens notepad
  T1218.007  Msiexec with a local MSI
  T1218.010  Regsvr32 with a local scriptlet/DLL
  T1218.011  Rundll32 with a benign local DLL export
  T1197      BITS job that copies a local file
  T1140      Certutil -decode of a local base64 file
  T1105      Certutil -urlcache against a local file/URL only

Prioritise T1218.007, T1218.003 and T1548.002: these are the techniques the
current model misses most often, so external evidence on them is the most
useful. One scenario per technique, repeated 2-3 times if time allows, so the
report can say how many runs were captured.

For each run: start the scenario marker, execute, stop, then export the Event
ID 1 rows whose UtcTime falls inside [start_utc, end_utc] and tag them with the
scenario_id. Include the parent process chain that Windows actually produced
(e.g. winword.exe -> cmd.exe -> certutil.exe).

6. MAPPING TO THE ML SCHEMA (YOUR ADAPTER, MY SCORING CONTRACT)
---------------------------------------------------------------
Per docs/issues.md, the schema adapter is your deliverable. The frozen XGBoost
model expects the same 108 columns used in
data/processed/sample_100k.parquet. The intended mapping is:

  process_name          <- lowercase basename(Image), e.g. "cmd.exe"
  parent_process        <- lowercase basename(ParentImage)
  command_line          <- CommandLine
  cmd_normalized        <- lowercase copy of CommandLine (rules only; the ML
                           text pipeline is separate)
  path_in_system32      <- 1 if Image contains \System32\
  path_in_syswow64      <- 1 if Image contains \SysWOW64\
  path_in_temp          <- 1 if Image path contains \Temp\ or \Windows\Temp\
  path_in_users         <- 1 if Image path contains \Users\
  path_in_programdata   <- 1 if Image path contains \ProgramData\
  process_is_powershell <- 1 if process_name in {powershell.exe, pwsh.exe}
  process_is_cmd        <- 1 if process_name == cmd.exe
  process_is_script_host<- 1 if process_name in {wscript.exe, cscript.exe}
  process_is_rundll32   <- 1 if process_name == rundll32.exe
  cmd_len, cmd_token_count, cmd_entropy, cmd_avg_token_len, cmd_pipe_count,
  cmd_amp_count, cmd_semicolon_count, cmd_redirect_count,
  cmd_backtick_count, cmd_quote_count, cmd_percent_count, cmd_dash_count,
  cmd_url_token_count, cmd_path_token_count, cmd_ip_token_count,
  cmd_b64_token_count   <- computed from CommandLine using the dataset
                           definitions; I can share the exact formulas
  flag_* (all 30)       <- regex/behaviour flags defined by the dataset; I can
                           share the full list and formulas
  parent_known          <- 1 if ParentImage is present and non-empty
  parent_is_office      <- 1 if parent in {winword.exe, excel.exe, powerpnt.exe,
                           outlook.exe, msaccess.exe, onenote.exe}
  parent_is_explorer    <- 1 if parent == explorer.exe
  parent_child_suspicious <- derived from (parent_is_office or parent_is_explorer)
                           and process in a LOLBin list; ask me for the exact
                           dataset definition
  signed_true           <- 1 if Get-AuthenticodeSignature(Image).Status is Valid,
                           0 if explicitly unsigned/invalid, missing if not checked
  network_connection_true <- 1 if a Sysmon Event 3 row exists for this ProcessId
                           within a short window, 0 if you observed none, missing
                           if Event 3 was not collected
  has_destination       <- 1 if that Event 3 row has a destination IP, else 0,
                           missing if not collected
  integrity_ordinal     <- ordinal of IntegrityLevel; ask me for the mapping
                           before filling it, otherwise leave missing

MISSING FIELDS: never invent a value. Leave NaN and list the column in
docs/vm_run_log.txt. XGBoost handles missing numeric values natively; the
categorical encoder already ignores unseen process names. Categorical values
must still be lowercase image names ("cmd.exe", not full paths).

Also record whether each scenario is attack or benign separately from the
features. Never put expected_label or technique_expected into a feature column.


7. WHAT I WILL DO WITH YOUR FILES
---------------------------------
1. Check that your adapted table has the 108 expected columns, correct names,
   lowercase categorical values, and explicit missing fields. We fix mismatches
   together before scoring.
2. Score with the frozen original XGBoost model at the validation-selected
   threshold (0.55) and with the SecureBERT branch if the command text is
   available.
3. Report scenario-level recall on attack runs, false-positive rate on benign
   runs, and a list of misses with raw command lines.
4. Write results/vm_* CSVs and a short note for the report. I will give you the
   numbers so you can describe the VM setup in your section; I will not claim
   more than the captured scenarios support.

This external check is small and qualitative. The report must say it covers
only the techniques that were actually run, on one VM, and is not a general
real-world estimate.
